## Common execution and rollback rules

Every slice reuses the accepted vehicle-owned evidence, exact identity, Working mutation engine and persistence validation. It must not simultaneously change qualification, provider materialisation and presentation. Retain the last Founder-accepted runtime as a rollback point; use a bounded presentation dispatch/feature switch only if explicitly authorised, never a platform-specific product fork. No simultaneous old/new writer to Working storage.

Retain the current browser-local Working store throughout U0–U6 unless a separate persistence programme is authorised. The 12-open-tab and six-derived-Table bounds may remain for regression safety and measured performance, but are provisional migration limits, not permanent professional limits. U1 must introduce the explicit protected-state capacity decision described in the [shell contract](01-shell-evidence-identity.md#provisional-capacity-and-protected-state); unchanged U0 does not authorise altering current tab behavior. The target capacity contract prohibits silently evicting Working history or a Table with unapplied input, Working changes or relevant history. Final capacity and any expansion/configurability require controlled measurements, professional workflow review and separate approval.

Application dependencies are authorised vehicle access, qualified Dataset/Definition outputs, independent capability contracts and published semantic bindings. Production obligations are exact identity, owner/vehicle isolation, immutable Current, explicit unknown/failure, source-lease separation and the explicit-token fail-closed boundary. Each slice is complete only when its stated acceptance, regression and Founder checkpoint are recorded; implementation success alone is not ratification or release authority.

Rollback means returning presentation dispatch to the last accepted path while preserving compatible evidence and browser Working. Do not delete histories, migrate schemas irreversibly or reinterpret new state under an older contract. If a later extension writes a new persistence version, it needs versioned coexistence and an explicit backwards-compatibility/rollback review before that slice begins. Reverting a UI is never permission to expose quarantined values or recover an invalid explicit session.

## Explicit exclusions and completion per slice

U0–U3 exclude new semantic Knowledge, renderer-derived axes, subscription enforcement and team persistence. U4 does not author semantic assertions from UI copy; producer extensions must follow existing governance and publication obligations. U5 excludes server Working synchronisation and changes to session/source-lease TTL. U6 is not a redesign opportunity. All slices exclude checksum algorithms, Export unlocking, Flash, Suggested generation, DTC operations and dyno control.

At each checkpoint record changed files, contract versions, fixtures and exact evidence identities, validation results, Founder observations, rollback path and unresolved concerns. The current three presentation failures remain named holds until the U4 contracts are implemented and accepted; they must not be counted as new regressions or silently deleted. Any other new failure stops advancement to the next slice until resolved or explicitly reviewed.

## Professional and dyno follow-on work

Before professional Workshop production completion, a separately governed server-side calibration revision and collaboration programme must satisfy the [mandatory future production gate](04-professional-dyno-boundaries.md#required-future-workshop-production-gate). Browser-only Working is insufficient for that completed product. The gate covers lineage, attribution, custody, notes/reviews, permissions, concurrency/conflict protection, branching/reconciliation, exact evidence associations, versioned migration/rollback and security/retention/customer consent. It is outside U0–U6 and authorises no database schema now.

Separately scoped programmes may deliver qualified Analysis/log handoffs, diagnostic capability or dyno evidence import. They consume the same core workspace contract and require their own production, persistence, security and validation review. Completing those features or the required future persistence programme is not a prerequisite for U0–U6 completion; U0–U6 completion must never be reported as professional Workshop production completion. Other TuneSight domains apply the product-wide invariant through their own bounded architecture and migration programmes.
