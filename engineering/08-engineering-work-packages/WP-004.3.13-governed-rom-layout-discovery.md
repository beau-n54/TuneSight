# WP-004.3.13 — Governed Candidate ROM-Layout Discovery and Selection

## Purpose

This work package introduces the pure domain step that precedes binary-to-ROM-layout membership qualification:

`Exact Engineering Binary → bounded identity observations → qualified candidate discovery → exact / ambiguous / unknown / conflict / invalid selection`

Discovery answers which currently qualified ROM Layout is responsible to evaluate. It does not establish that the binary is a qualified member of that layout.

## Authority boundary

The discovery registry is derived only from active `QualifiedRomLayoutApplicabilityRelationship` records and their exact `RomLayoutIdentity` records. Every descriptor binds the qualified applicability registry Snapshot, relationship revision and Definition Set revision. An unqualified XDF, readable Definition Set, filename, directory, byte similarity, successful raw read, engine family, container or size cannot enter or manufacture discovery authority.

The current real registry therefore contains only the four accepted N54 layouts. No B58 or other layout is admitted by this work package.

## Qualified descriptor

Each immutable descriptor preserves only searchable qualified Evidence:

- ROM Layout, relationship and Definition Set identities/revisions;
- ROM and calibration software identifiers;
- ECU/DME family;
- container and exact byte length;
- marker normalized forms, encodings/detectors, multiplicity and authoritative offsets;
- authority provenance, source disclosure and limitations;
- qualified registry Snapshot identity.

The complete Definition Set is deliberately not duplicated into discovery.

## Binary observations and candidate assessment

The request binds exact binary bytes and `EngineeringBinaryIdentity`, all credible `InternalIdentityObservation` records, the qualified discovery registry, optional independently qualified ECU-family Evidence, provenance and discovery contract version. Observations retain raw and normalized forms, detector/encoding, offsets, occurrence count, credibility basis and ambiguity.

Every qualified descriptor receives one explicit Evidence state:

- `strong_candidate`: identity and every required marker correspond exactly, with no contradiction or incompatibility;
- `possible_candidate`: some positive identity or marker Evidence exists, but discovery Evidence is incomplete;
- `contradicted`: material qualified-registry identity or marker-offset/multiplicity Evidence rejects the descriptor;
- `incompatible`: container, length or independently qualified family Evidence rejects the descriptor;
- `insufficient_evidence`: no responsible positive or contradictory conclusion exists.

Container, length and family are rejection filters only. They cannot create a candidate.

## Selection outcomes

- `exact_candidate`: exactly one strong candidate remains and no possible candidate overlaps it;
- `ambiguous`: multiple strong/possible candidates remain, or a lone merely possible candidate cannot be promoted to exact;
- `unknown`: no qualified descriptor is responsibly supported and available observations do not materially contradict the qualified vocabulary;
- `conflict`: qualified identity Evidence materially contradicts all otherwise available qualified layouts;
- `invalid`: exact byte identity, bounded input or qualified registry input cannot be safely assessed.

There is no score, winner, registry-order preference, first match, byte-similarity fallback or broad XDF search.

## Result Evidence and registry evolution

`RomLayoutDiscoveryResult` is immutable Evidence. It preserves the exact binary identity, qualified registry Snapshot, every candidate assessment, selected candidate or ambiguity set, contradicted layouts, missing Evidence, outcome, provenance, limitations, contract version and deterministic identity/revision. It explicitly records that no best-match heuristic was used and membership was not qualified.

The same exact binary, registry Snapshot and contract produce the same result identity. A new qualified registry Snapshot changes the result identity and may responsibly change an earlier exact result to ambiguous if newly admitted qualified authority overlaps it.

## Discovery and membership separation

`discoverAndQualifyBinaryRomLayout` calls the existing membership contract only after `exact_candidate`. The selected layout must have exactly one supplied membership authority binding its layout, active relationship, exact Definition Set and definitions. Discovery Evidence and membership Evidence remain separate objects. Ambiguous, unknown, conflict and invalid discovery never invoke membership.

The bounded proof continues from a newly modified IJE0S digest through discovery, membership, qualified extraction, engineering conversion and qualified comparison without caller-supplied IJE0S identity at discovery entry.

## BMW-wide and MG1 compatibility

The registry and engine contain no closed platform enum or N54 selection branch. Future qualified N55, S55, N13, N55E, B58 Gen1/Gen2, S58, S63 and other layouts can use the same descriptor contract after their applicability authority exists.

The observer and descriptor contracts support ASCII and encoded numeric markers, multiple credible observations, common and candidate-specific markers, authoritative offsets and incomplete identity Evidence. Controlled MG1-shaped proofs preserve overlapping numeric markers and return ambiguous rather than forcing an N54-style single-marker answer. Current master-library B58 marker Evidence may feed descriptors only after B58 applicability qualification; this work package does not resolve its detector or Stock Variant ambiguity.

## Exclusions and truthfulness

This package does not establish Stock authenticity, Stock Variant, VIN, exact vehicle, chassis, hardware modifications, engine condition, calibration semantics, safety, recommendations or BMW master coverage. It adds no runtime upload, persistence, network, Supabase, UI, Native Vehicle Data, WP-005.1, flashing, Calibration Knowledge binding, Suggested Calibration or Workshop behavior.

## Completion condition

Complete when deterministic tests prove descriptor/request/result identity and immutability; all eight current N54 binary instances; modified-content discovery; wrong-ROM, marker-offset, container/length, unknown, ambiguous and invalid outcomes; registry-order independence and evolution; MG1-shaped multi-marker ambiguity; discovery-to-membership separation; and extraction, conversion and comparison continuation, with relevant repository regressions clean.
