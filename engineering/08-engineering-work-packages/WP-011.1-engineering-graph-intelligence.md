# WP-011.1

## Engineering Graph Intelligence

---

## Objective

Improve the professional presentation, readability, inspection behaviour and engineering traceability of TuneSight telemetry graphs without altering telemetry values, calculations, pull detection, event detection, Evidence, Reasoning, confidence or engineering conclusions.

The graph shall help a calibration engineer determine:

1. what occurred during the recorded samples;
2. where it occurred;
3. which channels support an existing event;
4. how actual values relate to targets and related channels;
5. which exact graph region supports an existing engineering conclusion.

## Implementation Summary

### Trace Rendering

Related channel values are presented in common inspection charts without modifying their arrays. Boost Actual and Boost Target share one scale. Target channels use a dashed line pattern, so meaning does not depend on colour alone. Per-cylinder timing corrections share one graph and remain individually focusable.

Straight sample-to-sample segments are used. The renderer does not introduce spline overshoot, false peaks or false minima. Animation is disabled.

### Axes and Grid

Graphs use restrained horizontal gridlines, explicit units, readable tick formatting and data-bounded axes. Monotonic single-pull RPM data may use an RPM axis. A multi-pull record whose RPM resets uses the original sample sequence rather than drawing false backward RPM connections. Exact stored RPM remains available in tooltip inspection.

No RPM is estimated when RPM evidence is unavailable.

### Legend and Channel Focus

Each available channel has a labelled control containing its professional name, unit and solid or dashed trace indicator. An engineer may focus one channel while all other channels remain present but subdued.

### Tooltip

The tooltip presents the exact stored sample value, channel name, unit and exact stored RPM when available. It identifies active pull and event regions from supplied boundaries. It never presents interpolated values as sampled values.

### Pull and Event Regions

Existing pull and event `startIndex` and `endIndex` values are passed to the graph unchanged. Pull regions use restrained blue treatment. Event regions use restrained amber treatment and appear only on graphs containing an event's existing supporting channels.

Presentation does not infer, widen, narrow or create regions.

### Responsive and Accessible Presentation

Desktop presents two graph columns for professional density. Each graph provides a minimum inspection width and horizontal scrolling where the viewport is narrower, preserving labels, controls, traces and event regions rather than permanently hiding them.

Interactive controls have accessible group names, pressed state, keyboard focus visibility and usable target size. Target and actual traces differ by both colour and line pattern.

### Founder Refinement

Founder inspection of Christos' persisted three-pull analysis accepted the graph direction and identified three presentation refinements.

The telemetry inspection section and each Engineering Inspection Panel now reuse TuneSight's canonical `bmw-border` convention. The restrained blue, dark-blue and red edge treatment establishes the surface and panel hierarchy without framing minor controls, so telemetry traces remain visually dominant. Panel headers integrate the engineering panel name, grounded description, visible channel names, units, target line style and focus controls.

The horizontal axis now communicates the plotted engineering quantity explicitly:

- monotonic RPM records use `Engine Speed (RPM)`;
- non-monotonic multi-pull records use `Sample Sequence`; and
- sample-sequenced records state that exact stored RPM remains available through tooltip inspection.

The apparent empty space after the final populated chart was confirmed as an unused cell in the two-column desktop grid. The final unpaired chart now spans both columns. It was not zero-valued telemetry, an unavailable channel or an intentionally rendered empty chart. Legitimate zero-valued series remain valid telemetry, while missing telemetry continues to use the existing professional empty state.

### Final Panel Geometry Refinement

Every standard Engineering Inspection Panel now uses one shared fixed outer height with aligned header, plotting and footer rows. Header and footer content remains accessible through contained overflow where a narrow viewport requires additional wrapping rather than increasing the panel footprint or hiding engineering-critical controls.

The six-cylinder timing panel uses the intentional wide-panel contract and spans both desktop columns with its own standard wide height. Standard panels do not become wide because of title, description, legend or footer length. The shared geometry contains no platform-specific branch.

The no-telemetry state occupies the standard panel footprint. Grid rendering creates no placeholder panel and no unavailable channel is fabricated.

## Known Limitations

- Current persisted telemetry does not expose timestamps to the graph, so non-monotonic multi-pull data uses sample sequence rather than time.
- Event selection is not currently connected to graph selection; WP-011.1 displays every supplied relevant event region without introducing cause-ranking behaviour.
- The latest persisted Beau B58 Founder analysis contains no telemetry samples, pull windows or events, so populated B58 graph scaling and target-versus-actual behaviour could not be physically validated without a new log upload.
- The available browser-control surface did not expose viewport emulation. Mobile behaviour was validated through responsive implementation and CSS inspection, not a separate physical mobile viewport.
- Graph-specific component rendering infrastructure does not currently exist; pure presentation contracts and numerical transformation behaviour are covered with Node tests.
