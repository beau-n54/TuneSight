# WP-004.3.24 — Connected ROM / Definition Coverage Discovery Architecture

Status: read-only domain architecture established; no physical transport implementation; no applicability, publication, Workshop admission, or production Knowledge mutation

Founder requirement: **the BMW master XDF library is a bootstrap Calibration Definition source, not TuneSight's permanent closed list of supported ROMs.**

## Canonical architecture

Definition Source → Canonical Calibration Definition / Definition Set → applicability authority → qualified Dataset → Workshop.

`tunesight.canonical-definition-source.v1` identifies a source independently of format. Supported architectural formats are XDF XML, TuneSight-native packages, qualified external formats, governed cross-ROM correspondence, and qualified reverse-engineering Evidence. The canonical set binds the complete source revision to canonical Definition revisions. XDF remains one adapter, not a Workshop product concept.

The core Dataset and Workshop view-model path already consumes qualified Definition revisions, Definition Set revisions, applicability relationships, and Datasets. It does not require a physical XDF at presentation time. Current leaks are naming (`XdfDefinitionRevision`, `XdfSourceArtifact`) and the N54 development fixture provider, which reads fixed `.xdf` paths and constructs the canonical material in-process. Those are adapter/fixture leaks; the production target must inject canonical qualified sets rather than filenames.

## Connected DME contract

`tunesight.definition-coverage-discovery.v1` accepts an existing immutable read-only `EcuIdentityObservation`, an explicit trust classification, optional ECU family, optional legitimately read/supplied Engineering Binary digest/container/size and marker offsets, provenance, and limitations. It does not implement or alter THOR/MHD transport. It is independent of a hardcoded BMW family list.

The resolver produces exactly one outcome:

- `EXACT_DEFINITION_COVERAGE`: one exact identity match has already-qualified coverage; existing applicability, membership, Dataset, and Workshop gates may proceed.
- `CANDIDATE_DEFINITION_COVERAGE`: exact-identity candidate source exists but applicability is not qualified; no Tables or Workshop eligibility.
- `ROM_RECOGNIZED_DEFINITIONS_UNAVAILABLE`: ROM identity is registered but no responsible source exists; show “Calibration Tables awaiting qualification”.
- `NEW_ROM_DISCOVERED`: identity is outside the current registry; preserve discovery Evidence only.
- `CONFLICT`: observations or candidate coverage contradict; select nothing.
- `INVALID`: trustworthy identity/provenance is absent; select nothing.

Family match, filename similarity, numeric proximity, and shared ECU family never select a Definition Set. Candidate correspondence cannot authorize Table transplantation.

## Discovery Evidence and subscriber boundary

The deterministic new-ROM package preserves DME/vehicle family where available, ECU family, software and Calibration IDs, binary digest/container/size, marker offsets and multiplicity, related exact-identity candidates, provenance, conflicts, and limitations. Material changes revise the package. The state is always `discovery_evidence_only`.

Subscriber observations follow: observation → immutable Evidence → engineering review → exact Source Authority → applicability decision → independent publication → Workshop availability. A subscriber vehicle cannot silently modify authority, applicability, production Knowledge, or Workshop registries.

Cross-ROM evidence may preserve binary structure, known Definition-address correspondence, axis/value structure, ROM lineage, and qualified neighbouring revisions. Its contract is always `candidate_evidence_only`, `applicabilityAccepted: false`, and `tableTransplantAuthorized: false` until governed decisions exist.

## Workshop behaviour

Only `EXACT_DEFINITION_COVERAGE` is Workshop-eligible, and even then existing downstream gates remain mandatory. Recognized ROMs without coverage show truthful identity plus “Calibration Tables awaiting qualification”. New ROMs show discovery state. Candidate, conflict, and invalid states expose no authoritative Tables and never construct an empty fake Calibration.

## Future-platform proof

Tests use `FUTURE-DME` / `FUTURE-1`, absent from the BMW master library, through the same read-only contract without a hardcoded engine list. They prove deterministic discovery identity, binary digest preservation, canonical source-format neutrality, exact/candidate/unavailable/new/conflict/invalid outcomes, rejection of family/filename/numeric fuzzy assignment, no Workshop eligibility from candidate state, and no acceptance/publication side effects.
