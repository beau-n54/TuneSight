# WP-004.3.4 — Exact Definition-to-ROM Applicability Qualification

**Status:** Implementation Slice — Founder Authorised

## Problem

Structural XDF interpretation and deterministic raw extraction do not prove that a Definition Revision belongs to the Engineering Binary being read. A successful byte read is not applicability authority. TuneSight requires a separate deterministic, immutable and evidence-bearing gate before any later layer may treat decoded calibration instructions as authoritative calibrated-intent Evidence.

## Authority Boundary

This slice answers one question:

> Is this exact Definition Set Revision applicable to this exact Engineering Binary / ROM?

Applicability qualification remains separate from extraction. Qualification determines whether the definition belongs to the binary. Extraction determines what raw value is stored at a declared location. Both must succeed independently before the future calibrated-intent authority gate can open.

This slice creates no engineering-value conversion, equation execution, Calibration Knowledge semantic interpretation, Stock/Modified comparison, recommendation, editor, reconstruction, export, runtime integration or production Knowledge.

## Definition Set Revision

One exact XDF Source Artifact and its complete interpreted collection of Definition Revisions form one immutable Definition Set Revision. Stable Definition Set identity binds the exact source digest. Definition Set Revision identity additionally binds the sorted exact Definition source-binding digests.

Applicability is assessed once at this coherent source-revision boundary rather than through independent ROM matching for every contained Definition. A contained Definition may inherit exact applicability only when it belongs to the exact qualified source and Definition Set Revision, has a derived valid identity, preserves no individual conflict and has no applicability exception.

The existing 133 representation-conflicted Definitions do not inherit exact authority. Applicability Evidence may later help distinguish revision provenance, but this slice does not resolve units or conversion/equation representation conflicts.

## Exact Engineering Binary Identity

Engineering Binary identity is derived from the SHA-256 digest and byte length of the exact resolved engineering bytes. It preserves container type, original container byte length and container-resolution method. For a supported DTF, identity therefore binds the extracted Engineering Binary rather than merely the uploaded container filename.

Observed ROM family, software identity, calibration identity, internal ROM identifiers and their provenance remain additional identity Evidence. Filename, directory, family and size do not establish exact binary identity.

## Applicability Evidence

Evidence records stable identity, signal, qualification strength, supporting or contradictory relationship, exact Definition Set scope where applicable, exact binary digest scope where applicable, asserted value, provenance and explanation.

Supported signal classes are:

- exact digest pairing;
- exact internal ROM identifier;
- software identity;
- calibration identity;
- ROM family;
- source association;
- size compatibility;
- explicit applicability; and
- explicit exclusion.

Repository co-location and naming may establish a provisional source association for discovery. They do not establish qualified applicability. Exact XDF/BIN pairing requires separate qualified provenance or authoritative exact Stock Variant Knowledge.

## Qualification Outcomes

- **Exactly Applicable:** qualified or authoritative Evidence binds the exact Definition Set Revision and exact Engineering Binary, with no material contradiction; or authoritative exact Stock Variant Knowledge binds the exact binary to the exact XDF source.
- **Qualified Candidate:** provisional exact/source association or provisional exact Stock Variant Knowledge supports the relationship without sufficient exact authority.
- **Family Compatible:** ROM-family compatibility exists without exact software/calibration proof.
- **Conflicting:** material positive and negative applicability Evidence disagree, or exact Stock Variant Knowledge conflicts.
- **Unknown:** available Evidence is insufficient for exact, candidate, family or negative qualification.
- **Inapplicable:** qualified exclusion or incompatible ROM/software/calibration identity establishes non-applicability without competing positive authority.
- **Invalid:** required Definition Set or Engineering Binary identity input is structurally invalid.

Every result has deterministic result identity, preserves the evaluated Evidence and Stock Variant response, explains the outcome and records unresolved conditions. Results are recursively immutable at their public collection boundaries and qualification is side-effect free.

## Stock Variant Knowledge Integration

The existing Stock Variant Knowledge registry and runtime response are reused. No parallel stock identity system is created.

An `exact_verified` result may establish exact applicability only when exact SHA-256 and size match and the authoritative Stock Variant explicitly relates to the exact XDF Source Artifact, source digest or Definition Set Revision. An `exact_candidate` result with the same exact relationship remains a qualified candidate. Family-only, conflict, unknown, invalid and runtime-unavailable outcomes remain distinct.

The production authoritative Stock Variant registry is currently empty. This slice does not manufacture production records. Controlled synthetic Knowledge proves the deterministic contract.

## Calibrated-Intent Gate

No later authoritative calibrated-intent claim is permitted unless all four conditions hold:

1. exact Engineering Binary identity exists;
2. the Definition Set is exactly applicable;
3. the contained Definition Revision validly inherits applicability and is not conflicting; and
4. deterministic raw extraction succeeds.

This gate authorises only the possibility of later calibrated-intent Evidence. It performs no XDF equation execution or engineering-value conversion.

## Real Repository Validation

- N54 IJE0S uses real bundled XDF and stock-binary bytes to prove controlled exact pairing, internal-identifier corroboration and wrong-ROM rejection against INA0S.
- B58 Gen1 uses real `000030765A3C06` assets and remains a qualified candidate because repository association is provisional rather than authoritative.
- B58 Gen2 `00005D5532C808` and S63 `00004ACF0A3204` real assets prove generic family-compatible behavior without platform branches.
- Filename, directory and size-only fixtures prove that misleading or compatible metadata cannot manufacture exact authority.

These fixtures validate engine behavior. They do not publish production applicability Knowledge.

## Master-Library Applicability Coverage

The deterministic development report discovers 99 Definition Set source files across seven represented family directories. It observes 95 provisional XDF/BIN source associations and four unresolved sources. It establishes zero automatically exact applicability relationships.

This report is intentionally different from 99.87% structural extraction readiness. Repository association is classified as candidate discovery Evidence, not exact authority. Future qualified sources outside the BMW master library enter the same source/binary/Evidence pipeline; the library is not hardcoded as the permanent source ceiling and no closed engine or ECU enumeration exists.

## Security and Integrity

Qualification is deterministic, immutable, bounded by supplied collections, side-effect free and provenance-bearing. It performs no network access, persistence, Supabase mutation, arbitrary code execution, equation execution or output-based file write. Existing XDF structural and Engineering Binary container protections remain unchanged.
