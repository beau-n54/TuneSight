## Objective

Present existing runtime events, ranked causes, supporting evidence and rejected causes in a professional hierarchy without creating or altering engineering truth.

The shared Engineering Inspection Surface guides the engineer through Observation, Evidence, Reasoning, Confidence and the supplied Inspection Direction. It applies to every platform routed through the common analysis presentation; differences in available telemetry and engineering outputs produce truthful differences in content rather than platform-specific presentation systems.

## Repository Audit Finding

The repeated `WGDC Saturation` cards satisfy **Condition C: Runtime emits only generic WGDC Saturation**.

The runtime emits one distinct `wgdc_saturation` event for each qualifying pull window. Each event has its own stable event identifier, sample-index region, RPM range, supporting channels, average WGDC evidence and event confidence. Cross Reference preserves one reference per event.

The Reasoning engine supplies only generic saturation context derived from the existing average WGDC threshold. The Root Cause engine has no `wgdc_saturation` dispatcher and therefore supplies no ranked underlying root cause for these events. Repository evidence does not establish whether the underlying cause is mechanical, calibration-related or another specific diagnosis.

The former surface rendered each event as an equal-weight card whose title was the humanised event type. Distinct observations therefore appeared to be repeated competing root-cause claims even though no specific root cause had been established.

## Implemented Presentation Contract

### Repeated Observations

Multiple unresolved `wgdc_saturation` events are grouped under the observed condition `WGDC Control Saturation`.

The group states that repeated control saturation is established while the underlying mechanical or calibration cause remains unresolved. Every distinct observation retains:

- event identity;
- RPM region;
- event confidence;
- average WGDC;
- event evidence;
- supporting channels; and
- existing reasoning context.

Identical event references are not rendered twice. Distinct events are never deleted or flattened.

### Event and Cause Separation

`WGDC Control Saturation` is labelled as a repeated observed control condition, not as an established root cause. No cause-family label is introduced because the current runtime does not provide a qualified cause-family contract for these events.

### Ranked Causes

Where the runtime already provides ranked root causes:

- the existing `primary` cause is presented as the dominant Primary Engineering Result;
- existing `secondary` and `tertiary` causes remain ordered and subordinate as alternative causes;
- cause confidence is displayed unchanged; and
- existing evidence, diagnostic ranking and inspection direction remain available.

Presentation performs a stable ordering by the supplied runtime rank. It does not calculate rank or confidence.

### Rejected Causes

Existing rejected causes remain visible with their supplied confidence and rejection reason. Presentation does not create new rejected causes or explanations.

### Final Founder Presentation Refinement

The shared analysis surface now places the Engineering Summary immediately after analysis identity and status. Explicit event-level `primary` Root Cause results follow as prominent, event-scoped Primary Engineering Results before the Engineering Inspection Panels. The surface states that these results are scoped to their detected events and are not a global diagnosis.

Repeated detected event types are grouped non-destructively into one event-family card. Each observation preserves event order, identity, pull relationship where resolvable, RPM range, severity, event confidence, metrics, evidence and channels. A single event continues to render without a repeated-family wrapper.

Christos' repeated `lean_under_load` events have no authoritative `rootCauses` output. They therefore remain an observed event family with the explicit statement that no authoritative cause ranking is available. Generic likely-cause context is not promoted into the Primary, Alternative or Rejected hierarchy.

Analysis-wide tune context generated by the existing `tuneNotes()` contract is rendered once as Global Tune Notes. Exact source-grounded prefixes identify global context, exact duplicate text is deduplicated and source event IDs remain recorded. All other notes remain Event-Specific Notes attached to their Cross Reference. Similar but non-identical notes remain separate.

## Known Limitation

The current runtime does not provide a ranked underlying root cause for `wgdc_saturation`. WP-011.2 therefore cannot present a specific Primary Cause for that condition without exceeding Presentation ownership. Deeper differentiation requires separately authorised work in the engineering domain that owns cause generation.

The current runtime also provides no authoritative ranked Root Cause for `lean_under_load`. Root Cause rank remains event-scoped, and Presentation does not construct a global ranking across unrelated events.

For this reason, WP-011.2 is **Partially Complete**. The truthful presentation-safe subset is implemented; the missing cause contract is explicitly preserved rather than fabricated.

Presentation is not hiding a Lean Under Load ranking: the Root Cause engine produces no authoritative Root Cause output for that event family. The missing capability belongs to Engineering Domain 05 — Explanation and future WP-007 work. WP-011.2 shall not invent, infer or promote a ranking.

WP-011.2 completion depends on future WP-007 Explanation coverage for event families lacking authoritative Root Cause output, beginning with Lean Under Load. The accepted partial implementation remains retained.
